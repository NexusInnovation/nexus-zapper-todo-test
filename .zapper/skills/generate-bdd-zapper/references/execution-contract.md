# Execution contract

How the suite is run and how its results are read. It is stack-agnostic: this stage defines the
contract, the project fills it in during implementation.

## Rules

- **One command runs the whole suite**, from the repository root, with no argument required. It
  is recorded in the `run-command` field of `.zapper/behaviour-driven-development/README.md`.
- **Results are machine-readable**: [Cucumber JSON](https://github.com/cucumber/cucumber-json-schema)
  (`cucumber-json`) or JUnit XML (`junit-xml`). The format is recorded in `result-format` and the
  path the command writes to in `result-file`, under `results/`.
- **The glue is project-specific.** Step definitions are generated by agents during implementation
  and are never written by this stage. Examples: Gherkin translated into Playwright tests in an
  existing codebase; a test framework scaffolded first for a vibe-coded prototype.
- **Exit code**: non-zero when at least one scenario fails, is undefined or pending.
- **Manual checks are excluded from the command.** A scenario tagged `@manual` (a non-functional
  check no automation can make) is filtered out by the run command itself (for example a tag
  expression `not @manual`), so that it is neither run nor reported as skipped. It is a known
  `manual` result, never a silent skip.
- **Performance data.** A scenario that uses the step `Given the realistic-volume dataset is loaded`
  runs on the `performance-dataset` of `.zapper/config.md`; the glue loads it with the command that
  field gives. The single run command includes these scenarios.
- **One copy of the `.feature` files.** They live in the folder named by `features-path`. When the
  project's runner needs them elsewhere (inside its test project), they are moved there and
  `features-path` is updated; a copy is never kept. Every stage locates them through
  `features-path`.

## Fields in README.md

```yaml
status: draft
features-path: .zapper/behaviour-driven-development/stories   # repository-relative; the test project folder once moved
run-command:                  # empty until the project has a runner
result-format:                # cucumber-json | junit-xml
result-file:                  # for example results/cucumber.json
```

An empty `run-command` means the suite is not runnable yet. This is expected before
implementation; it is not an error and no result is invented. The stage that makes the suite
runnable writes `features-path`, `run-command`, `result-format` and `result-file` back here; the
Run operation writes the results back (`results.md` and the **Last run** column).

## Reading the results

The scenario-to-requirement link is the `@<requirement-id>` tag of each scenario.

- **Cucumber JSON**: each element's `tags` lists its requirement tags. A scenario is `passed` only
  if every step and every reported hook (`before`, `after`) has the status `passed`. Any other
  status (`failed`, `undefined`, `pending`, `skipped`, `ambiguous`, `unknown` or an unlisted one)
  makes it `failed`.
- **JUnit XML**: each `testcase` is a scenario; requirement tags must be present in its name or in
  a `properties` entry. If the runner does not emit them, match by scenario name only when it
  identifies a single scenario of the suite, and use the `classname` or file to tell the story
  apart. A testcase that cannot be tied to one story and scenario is reported as unmapped and is
  credited to no requirement.

A requirement is `failed` if one of its scenarios failed. Otherwise it is `passed` only when every
scenario that verifies it has a result and all passed; `not run` if at least one of its scenarios
has no result (including when only some of them ran).

A requirement whose scenarios are all tagged `@manual` has the status `manual`: it has no result by
design, is not a failure and not `not run`, and must always be listed with its reason. When some of
its scenarios are manual and others automated, its status comes from the automated ones and the
manual scenarios are listed apart.

## results.md (per story)

Written by the Run operation, overwritten on each run.

```markdown
# Results: <story title>

Run: <ISO date and time> · Command: `<run-command>`

| Requirement | Scenarios | Status |
| ----------- | --------- | ------ |
| 1234-R01    | 2         | passed |
```

Statuses: `passed`, `failed`, `not run`, `manual`. List failed scenario names with the first
failing step below the table. For a performance requirement, add the measured value against the
threshold when the result file carries it. List each manual scenario with its reason.
