# BDD suite layout

The contract of `.zapper/behaviour-driven-development/`. Later stages (plan, implementation,
hooks) rely on it, so follow it exactly.

## Folder

```text
.zapper/behaviour-driven-development/
├── README.md                       # status marker, run contract, index
├── results/                        # raw machine-readable output of the last run
└── stories/
    └── <story-slug>/               # same slug as .zapper/input/stories/<story-slug>/,
        │                           # or nfr-<category> for non-functional requirements
        ├── <story-slug>.feature
        └── results.md              # outcome of the last run for this story
```

Create no other file at the root of `.zapper/behaviour-driven-development/`. The step
definitions (glue) are not part of this folder: they are project-specific and generated by agents
during implementation, in the project's own test folder.

### Where the `.feature` files live

`stories/` is the location until the runner is wired. `wire-bdd-zapper` then moves the `.feature`
files into the project's test project and records that folder as `features-path`; from then on
every operation of this skill reads and writes the `.feature` files in `features-path`, with the
same `<story-slug>/<story-slug>.feature` layout, and creates no `.feature` file under `stories/`.
`results.md` always stays in `stories/<story-slug>/`.

## README.md and the status marker

- YAML frontmatter `status: draft | approved`. It is the only approval signal later stages and
  hooks check. The suite is only approved when every `.feature` file was reviewed by the team.
- Any generated change to a `.feature` file sets it back to `draft`. Only the
  walkthrough sets `approved`. Once `approved`, `.feature` files are read-only to agents (enforced
  by a hook, ADO 76648).
- The frontmatter also holds the run contract (`features-path`, `run-command`, `result-format`,
  `result-file`).
- **Stories** table: one row per story and per non-functional category with its link, its number of
  requirements and scenarios, and its last run outcome.

## Story folder

One folder per story of `.zapper/input/stories/`, with the same slug. A story without acceptance
criteria has no folder; report it instead.

## Non-functional requirements

The non-functional requirements (`.zapper/input/non-functional-requirements.md`) are requirements
of the suite like the acceptance criteria, so that quality is part of "done". Each category that
holds at least one requirement is a pseudo-story in `stories/`, with the same layout as a story:

- Folder, `.feature` file and story key: `nfr-<category>`, with `<category>` one of `security`,
  `performance`, `accessibility`, `localization`, `observability`, `other`. It has no counterpart
  in `.zapper/input/stories/`; the source is one bullet of the category per requirement.
- Requirement ID: `nfr-<category>-R<nn>`, for example `nfr-performance-R01`, with the stability
  rules of the story IDs below.
- Each requirement has at least one scenario. Either it is automated, or it is tagged `@manual`
  (no automated check is possible): a `@manual` scenario is excluded from the run command, its
  requirement has the status `manual` in the results, and the report lists it. It is never
  skipped silently.
- Performance scenarios use the realistic-volume dataset of `.zapper/config.md`
  (`performance-dataset`) and state their thresholds in their steps; approving the suite approves
  them. Rules: [../steps/non-functional-checks.md](../steps/non-functional-checks.md).

## Requirements

A requirement is one acceptance criterion of the story. The suite stores no copy of it: the
criterion lives in `.zapper/input/stories/<story-slug>/`, and its ID lives only in the
`@<requirement-id>` tags of the scenarios that verify it. While a skill operation runs, the
criteria and their IDs are listed in a temporary working list (see
[../steps/derive-requirements.md](../steps/derive-requirements.md)), rebuilt from the input and the
tags each time and discarded when the operation ends.

### Requirement ID

`<story-key>-R<nn>`, with `nn` a two-digit counter per story starting at `01`.

- `<story-key>` is chosen once, when the story is first added, and then never changes, even when
  siblings are added or removed: the leading source ID of the story slug (for example `1234` for
  `1234-add-item-to-cart`). If another story's tags already use that source ID, or the slug has
  none, use the whole slug. For a new story, check the keys used by the tags of the suite;
  existing stories keep theirs.
- IDs are stable: a criterion keeps its ID while it exists, even when reworded or reordered. A
  new criterion takes the number after the highest one of its story. When a criterion is removed,
  its tag is removed from the scenarios (see [../flows/update.md](../flows/update.md)).
- Examples: `1234-R01`, `1234-R02`. A non-functional requirement uses the key of its category:
  `nfr-performance-R01`.

## Feature file

- One `.feature` file per story, named `<story-slug>.feature`.
- Gherkin syntax and keywords follow the
  [Cucumber Gherkin reference](https://cucumber.io/docs/gherkin/reference): `Feature`,
  `Scenario` (or `Scenario Outline` with `Examples`), `Given` / `When` / `Then`, optional
  `Background`, `And` / `But`.
- Writing rules and tagging: [../steps/write-features.md](../steps/write-features.md).
- Every scenario carries a tag `@<requirement-id>` for each requirement it verifies. The tags are
  the only link between the acceptance criteria and the scenarios.
