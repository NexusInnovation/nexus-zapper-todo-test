# Package

Turns the signed-off run into the final artifact: code, tests and report, clean and versioned on the
feature branch, ready for the human to open as a pull request into the default branch. The code
and tests are already committed by the run; this operation versions the report with them and
publishes the branch.

## Before Starting

1. Read `.zapper/run/output-report/summary.md`. Package only when `sign-off: signed-off` and
   `hard-validations: passed`. Otherwise stop and tell the user which operation comes first
   ([generate.md](generate.md) or [sign-off.md](sign-off.md)).
2. Check that `commit` of the report is an ancestor of `HEAD`, and that every file changed since
   (committed or not) is one of the
   [files that do not invalidate the evidence](../references/report-layout.md#files-that-do-not-invalidate-the-evidence).
   Otherwise the sign-off no longer covers the change: stop, and commit it then regenerate the
   report.
3. Get the default branch with `git symbolic-ref --short refs/remotes/origin/HEAD`. If the current
   branch is the default or a protected branch, stop: the artifact never goes through it.

## Step 1: Clean the working tree

Run `git status`. Nothing the run generated by accident may be versioned: no build output, caches,
temporary files, credentials or raw logs outside what the report links to.

- Files that belong to the artifact are kept: the report, the BDD results files, and the
  `.zapper/run/` files the report links to. Code and tests are already committed (see Before
  Starting).
- Anything else: show the list and ask the user what to do with each file. Never delete a file or
  discard a change without an explicit answer, and never rewrite history.
- If a file looks like a secret (connection string, key, token, password), stop and tell the
  user instead of staging it.

## Step 2: Commit

Stage the report, the BDD results files and the run files it links to explicitly by path (never `git add -A`), and commit
them following the commit convention of the project's repository instructions. Do not skip hooks.
The report's `commit` field remains the commit it was generated at, and the diff since is only
the report and the BDD results.

## Step 3: Verify

After the commit, run `git status` and confirm the tree is clean and `HEAD` is on the feature
branch. The BDD suite and the build ran at the recorded `commit`; run nothing again unless
something other than the report changed.

## Step 4: Push the feature branch

Ask the user to confirm, then push only the feature branch to `origin`, setting its upstream. Never
push to the default or a protected branch and never force-push. Do not open or merge the pull
request: that is the human's.

## Step 5: Report to the user

Give the branch name, the commit list against the default branch, and the suggested pull request
title and description from the **Pull request** section of the summary, so the human can open it.

## Checklist

- [ ] The report was signed off, passed, and no code changed since.
- [ ] The working tree is clean, with no accidental file versioned and no secret.
- [ ] The commits are on the feature branch, which was pushed, and the default branch was not
      touched.
- [ ] No pull request was opened or merged.
